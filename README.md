# Проектирование автоматизированной системы риск-менеджмента финансовой устойчивости компании (FinRisk-Monitor)

Репозиторий содержит материалы курсовой работы по проектированию автоматизированной системы мониторинга и прогнозирования финансовых рисков в рамках риск-ориентированного подхода.

## 📋 1. Реестр требований к системе

### Функциональные требования (Functional Requirements, FR)
* **FR-1: Сбор и агрегация данных.** Система должна в режиме реального времени принимать потоковые данные о финансовых транзакциях (поступления, списания) и актуальных остатках на расчетных счетах компании.
* **FR-2: Расчет финансовых метрик.** Система должна автоматически рассчитывать коэффициенты финансовой устойчивости (абсолютной, текущей и быстрой ликвидности) при изменении баланса по счетам.
* **FR-3: Прогнозирование кассовых разрывов.** Система должна строить платежный календарь на основе исторических данных и запланированных платежей для выявления рисков дефицита ликвидности (кассовых разрывов) на горизонте до 30 дней.
* **FR-4: Контроль риск-лимитов.** Система должна сопоставлять текущие и прогнозные метрики с установленными пороговыми значениями (Risk Appetites / Limits).
* **FR-5: Информирование и алертинг.** Система должна мгновенно генерировать системные оповещения (алерты) при пересечении риск-метрик зон толерантности («желтая» и «красная» зоны риска).

### Нефункциональные требования (Non-Functional Requirements, NFR)
* **NFR-1: Производительность (Performance).** Время обработки транзакции API-сервисом и пересчета базовых коэффициентов ликвидности не должно превышать **500 мс** с момента получения пакета данных.
* **NFR-2: Доступность (Availability).** Коэффициент доступности системы должен составлять **99.9% (High Availability)**, обеспечиваемый развертыванием в отказоустойчивом кластере.
* **NFR-3: Безопасность (Security).** Доступ ко всем эндпоинтам API и интерфейсу системы должен быть защищен по протоколу HTTPS с авторизацией на базе токенов JWT (или протокола OAuth 2.0). Данные о счетах должны быть зашифрованы на уровне БД (TDE).
* **NFR-4: Масштабируемость (Scalability).** Архитектура должна поддерживать горизонтальное масштабирование (Horizontal Pod Autoscaling) для обработки пиковых нагрузок до **100 RPS** (Request Per Second) в моменты закрытия банковских дней.

## 👥 2. Сценарии использования (Use Cases)

### Use Case 1: Мониторинг и управление лимитами риска
* **Актер:** Риск-менеджер (Risk Manager)
* **Предусловие:** Пользователь авторизован в системе, открыта панель администрирования риск-политик.
* **Основной сценарий (Main Flow):**
  1. Риск-менеджер выбирает конкретную метрику риска (например, *Коэффициент абсолютной ликвидности*).
  2. Система отображает текущее значение лимита и историю его изменений.
  3. Риск-менеджер вводит новые пороговые значения для «желтой» (предупредительной) и «красной» (критической) зон.
  4. Риск-менеджер сохраняет изменения.
  5. Система валидирует корректность введенных диапазонов данных.
  6. Система обновляет параметры конфигурации модуля алертинга (Risk Engine) в оперативной памяти и фиксирует изменения в аудит-логе.
* **Постусловие:** Новые лимиты применяются ко всем входящим транзакциям в режиме реального времени.

### Use Case 2: Анализ прогнозных кассовых разрывов
* **Актер:** Финансовый аналитик (Financial Analyst)
* **Предусловие:** Модуль прогнозирования завершил ежедневный цикл расчета платежного календаря на основе исторических данных и реестра счетов.
* **Основной сценарий (Main Flow):**
  1. Финансовый аналитик запрашивает дашборд «Платежный календарь и Прогноз ликвидности».
  2. Система визуализирует график совокупного остатка денежных средств по дням на выбранный период (30/60/90 дней).
  3. Система подсвечивает дату потенциального кассового разрыва (где сальдо опускается ниже нуля).
  4. Финансовый аналитик кликает на проблемную дату.
  5. Система детализирует плановые поступления и списания на этот день, группируя их по статьям движения денежных средств (ДДС).
  6. Аналитик инициирует симуляцию сдвига планового платежа на более поздний срок.
  7. Система мгновенно пересчитывает прогнозный баланс и убирает маркер кассового разрыва.
* **Постусловие:** Сформирован аналитический сценарий оптимизации платежей для предотвращения риска.

## 🗄️ 3. Логическая структура базы данных

Данные организованы в реляционной модели (3NF). Отношения между ключевыми таблицами построены по принципу **Один-ко-многим (1:M)**:

* **Accounts** (Расчетные счета компании)
  * `account_id` (UUID, PK) — Уникальный идентификатор счета.
  * `account_number` (VARCHAR) — Номер расчетного счета.
  * `bank_name` (VARCHAR) — Наименование банка.
  * `currency` (VARCHAR) — Валюта счета (ISO 4217).
  * `current_balance` (NUMERIC) — Текущий подтвержденный остаток.
  * `updated_at` (TIMESTAMP) — Время последнего обновления баланса.

* **Transactions** (Финансовые транзакции) — *Связь с Accounts (1:M)*
  * `transaction_id` (UUID, PK) — Идентификатор транзакции.
  * `account_id` (UUID, FK) — Ссылка на расчетный счет.
  * `direction` (VARCHAR) — Направление (`IN` / `OUT`).
  * `amount` (NUMERIC) — Сумма транзакции.
  * `counterparty_inn` (VARCHAR) — ИНН контрагента.
  * `purpose` (TEXT) — Назначение платежа.
  * `value_date` (TIMESTAMP) — Дата проведения платежа.
  * `created_at` (TIMESTAMP) — Дата записи в систему.

* **RiskLimits** (Лимиты риска) — *Связь с Accounts (1:M)*
  * `limit_id` (UUID, PK) — Идентификатор лимита.
  * `account_id` (UUID, FK, Nullable) — Ссылка на конкретный счет (если пусто — лимит действует на всю компанию).
  * `metric_name` (VARCHAR) — Код метрики (например, `CURRENT_LIQUIDITY`).
  * `yellow_zone_threshold` (NUMERIC) — Порог предупредительной зоны.
  * `red_zone_threshold` (NUMERIC) — Порог критической зоны.
  * `is_active` (BOOLEAN) — Флаг активности правила.

* **SystemAlerts** (Системные алерты) — *Связь с RiskLimits (1:M)*
  * `alert_id` (UUID, PK) — Идентификатор алерта.
  * `limit_id` (UUID, FK) — Ссылка на нарушенный лимит.
  * `actual_value` (NUMERIC) — Зафиксированное критическое значение метрики.
  * `severity` (VARCHAR) — Статус критичности (`WARNING` / `CRITICAL`).
  * `status` (VARCHAR) — Статус обработки (`NEW` / `ACKNOWLEDGED` / `RESOLVED`).
  * `triggered_at` (TIMESTAMP) — Время фиксации инцидента.
